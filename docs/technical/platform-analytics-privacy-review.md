# Privacy review for platform analytics

Reviewed on 30 September 2026 against the in-progress CinemataCMS tracker and self-hosted Umami v3.4.0. This review covers King's request for site traffic, visitor segments, homepage and media journeys, and text-page readership. It is a design decision for future admin reports, not evidence that production collection is active.

## Decision

Build aggregate site reports and journeys for **public pages** first. Show page views, visits, estimated visitors, referring domains, country, and broad browser, OS, and device categories to authorized platform administrators. Use named events for homepage clicks, media-page actions, and sign-up or sign-in link clicks. Count article page views where each article has its own public URL.

Do **not** send an account ID, an account-derived hash, a role, or an Umami Distinct ID to the collector for these reports. Do not add a `user_type` session property. Following the review, the requested role split was implemented as daily CMS counts for anonymous, regular, trusted, and curator viewers. These counts have no visitor or session key. Keep private, restricted, and unlisted media out of platform journey and role reports, even though the accepted owner-analytics design tracks accessible media. Keep the owner dashboard free of visitor demographics and role segments.

This is a privacy-minimizing recommendation, not a legal finding that the data is anonymous. Umami v3.4.0 creates a session ID from the website or source ID, IP address, user agent, and a rotating salt. It stores events under that session ID, and its Sessions view can show one session's activity. Adding an account role would connect that role to a page and event timeline, even without a Distinct ID. Umami's [v3.4.0 collection code](https://github.com/umami-software/umami/blob/v3.4.0/src/app/api/send/route.ts#L152-L198), [session data write](https://github.com/umami-software/umami/blob/v3.4.0/src/app/api/send/route.ts#L292-L325), and [Sessions documentation](https://docs.umami.is/docs/sessions) establish that behavior. The [EDPB's pseudonymisation guidance](https://www.edpb.europa.eu/news/edpb-adopts-pseudonymisation-guidelines-and-paves-the-way-to-improve-cooperation-with_en) also cautions that data linkable to a person with other information remains personal data under the GDPR.

## How the wishlist maps to the data

| Request | Recommendation and limit |
| --- | --- |
| Page views and visits | Use Umami's aggregate counts for admin reports. A visit is a session activity window, not a person; v3.4.0 starts a new visit after 30 minutes of inactivity in its [collection code](https://github.com/umami-software/umami/blob/v3.4.0/src/app/api/send/route.ts#L184-L198). |
| Unique visitors | Label this **estimated visitors**. Umami's rotating session hash cannot count distinct people across shared devices, networks, or browsers. Keep it out of creator reports, as the current [analytics guide](analytics.md#owner-dashboard) requires. |
| Referrer | Keep the present domain-only browser payload. Full referring paths and queries can disclose tokens or sensitive routes; Umami v3.4.0 [can store both](https://github.com/umami-software/umami/blob/v3.4.0/src/app/api/send/route.ts#L200-L279). |
| Country, browser, OS, device | Show broad aggregate categories. Country is derived from the IP or trusted location headers. Verify that the deployed collector stores **country only** before enabling the country report; Umami v3.4.0 can also derive and store region and city by default through [location lookup](https://github.com/umami-software/umami/blob/v3.4.0/src/lib/detect.ts#L87-L147). The current browser allowlist omits screen size, so check device-category accuracy before publishing it. |
| Anonymous, regular, trusted, curator | `users.User.advancedUser` is labeled **Trusted User**; there is no separate Advanced tier. The CMS stores daily public event counts by these four groups without a visitor, session, or media ID. Curator activity counts; Django staff, editors, managers, and superusers remain excluded. The admin report omits counts below 10. Review the visitor notice and processing purpose before activation. |
| Homepage and media journeys | Use aggregate Umami journeys for public pages and named CTA events. Count a click to Sign up or Sign in, not form contents or the identity of the person who authenticates. Exclude nonpublic media IDs from admin journey definitions. Umami's [journey query](https://github.com/umami-software/umami/blob/v3.4.0/src/queries/sql/journeys/getJourney.ts#L74-L130) groups paths and events by visit. |
| Blog, Curator Voices, other text pages | Count each public `Page` URL. The tracker also emits once-per-load thresholds at 15, 30, 60, 120, and 300 seconds while the page is visible and focused. These are foreground-time bands, not proof of reading. A landing page containing several articles cannot establish which article was read. |

## Current controls and remaining exposure

The in-progress [CMS privacy boundary](../../cms/analytics.py) suppresses the browser tracker for staff and users who disable activity logging, and emits media data only after an access check. Curators are included as viewers. The [browser tracker](../../static/js/cinemata-analytics.js) strips search strings, hashes, titles, access tokens, and user identifiers from Umami payloads. It sends a generic path and no referrer for nonpublic media. The [playback endpoint](../../cms/playback_analytics.py) records watch summaries without a viewer account ID. Public role counts go to the CMS through a signed, same-origin request; the browser does not send the role. These are application controls; the collector still receives a request IP and user agent to create its session hash and location data. [Umami's v3.4.0 detection code](https://github.com/umami-software/umami/blob/v3.4.0/src/lib/detect.ts#L87-L147) describes that processing.

The stable media UUID in an event can be mapped back to a film by an operator. For a film with few authorized viewers, a session timeline may reveal viewing behavior. This is an inference from the current payload and Umami's session model. Restrict Umami account access, avoid share links that expose Sessions or Journeys, and keep nonpublic media out of platform reports. The owner dashboard remains current-owner scoped in the CMS. [Umami's sharing guide](https://docs.umami.is/docs/enable-share-url) shows that share links can expose report sections.

The 12-month Umami purge job and CMS purge of playback summaries and daily role counts are prepared for the local OrbStack setup; [the integration guide](analytics.md#retention-and-rollout) does not claim production activation. Before any staging or production activation, verify the version-pinned purge against the deployed schema, the backup expiry, collector access-log exception, Umami admin permissions and share links, and a captured payload from each public and nonpublic path. A database check must confirm whether region and city are absent. Umami's `SKIP_LOCATION_HEADERS` setting alone is insufficient: its [v3.4.0 code](https://github.com/umami-software/umami/blob/v3.4.0/src/lib/detect.ts#L106-L147) falls back to a GeoLite city database. A country-only GeoLite database is one configuration to test, not an assumed production setting.

## Legal and future-product questions

Review the visitor notice, lawful basis, objection path, and relevant jurisdictions before activation, including the new role-aggregate purpose. DNT and the account's activity-logging switch are implemented controls, but they do not settle every local consent rule. France's [CNIL audience-measurement guidance](https://www.cnil.fr/en/sheet-ndeg16-use-analytics-your-websites-and-applications) illustrates how narrow a consent exemption can be and warns that national ePrivacy rules differ. Offering the resulting insights in a paid tier would change the access audience and needs a separate review.
